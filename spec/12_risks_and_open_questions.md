# 12. Риски и открытые вопросы

## Критичные риски

### Риск 1. Открытие двух ячеек одновременно

Проблема:

- пользователь может взять товар не из той ячейки;
- учет может разъехаться;
- физическая безопасность ухудшается.

Защита:

- backend-проверка активной сессии;
- partial unique index в PostgreSQL;
- тест конкурентных запросов;
- блокирующий экран UI.

## Риск 2. Остаток изменился до физического действия

Проблема:

- система может списать или добавить товар, хотя пользователь ничего не сделал;
- ошибка при открытии замка может испортить учет.

Защита:

- остатки менять только после `confirm-close` и финального подтверждения операции;
- отмена не меняет остатки;
- ошибка оборудования переводит сессию в `error`.

## Риск 3. Перезапуск во время открытой ячейки

Проблема:

- backend потерял состояние;
- неизвестно, закрыта ли ячейка;
- неизвестно, был ли взят товар.

Защита:

- хранить сессию в БД;
- при старте искать активную сессию;
- не завершать ее автоматически;
- показывать блокирующий экран.

## Риск 4. Неправильная привязка реле к ячейке

Проблема:

- система думает, что открывает ячейку 2, но открывается ячейка 3.

Защита:

- таблица `cells` с controller/channel;
- hardware smoke-test каждого канала;
- маркировка проводов;
- тестовая команда открытия из админки.

## Риск 5. Некачественные замки или питание

Проблема:

- замок не открывается;
- реле щелкает, но тока не хватает;
- блок питания проседает.

Защита:

- отдельный блок питания 12 В;
- запас по току;
- тест под нагрузкой;
- логирование ошибок;
- выбор fail-secure замков.

## Риск 6. RFID-считыватель дает разный формат UID

Проблема:

- один и тот же ключ может читаться с префиксом, суффиксом или Enter;
- авторизация будет нестабильной.

Защита:

- нормализация UID;
- лог неизвестных UID;
- тест нескольких карт;
- настройка считывателя.

## Риск 7. Пользователь подтвердил закрытие, но ячейка физически открыта

Проблема:

- в MVP закрытие ручное;
- пользователь может ошибиться.

Защита MVP:

- крупный экран с инструкцией;
- ответственность пользователя;
- журнал действий.

Защита будущей версии:

- датчик закрытия;
- запрет продолжения, если датчик показывает открыто.

## Риск 8. Ручная корректировка остатков без истории

Проблема:

- учет становится непрозрачным.

Защита:

- все изменения через `stock_movements`;
- ручная корректировка только как `adjust` или `inventory`;
- запрет прямого изменения `stock_items` из UI без истории.

## Открытые вопросы

### 1. Какой формат идентификатора товара главный?

Варианты:

- barcode;
- SKU;
- внутренний ID;
- external_id.

Рекомендация MVP:

- barcode для точного поиска сканером;
- SKU для внутреннего артикула;
- name для ручного поиска;
- external_id зарезервировать для интеграции.

### 2. Нужны ли дробные количества?

Сейчас количество заложено как `Numeric`.

Если всегда штуки, можно отображать без дробной части. Но хранить `Numeric` полезно для будущих единиц вроде метров, упаковок, килограммов.

### 3. Может ли `user` смотреть историю товара?

Варианты:

- запретить;
- разрешить только свою историю;
- разрешить всю историю.

Рекомендация MVP:

- `admin` и `manager` видят историю;
- `user` не видит или видит ограниченно.

### 4. Нужен ли PIN после RFID?

Для MVP не нужен.

Можно добавить позже, если RFID-карты будут часто теряться или передаваться между людьми.

### 5. Нужен ли таймаут открытой операции?

Желательно, но аккуратно.

Автоматически менять остатки нельзя. Можно:

- показывать предупреждение;
- писать `session_timeout`;
- требовать администратора.

### 6. Нужно ли автоматическое закрытие сессии по датчику?

В будущей версии можно.

Но даже с датчиком финальное изменение остатка лучше оставлять за явным подтверждением пользователя, иначе система не узнает, сколько товара реально положили или забрали.

### 7. Как делать интеграцию с внешними системами?

Минимально заложить:

- `products.external_id`;
- API для товаров;
- API для остатков;
- API для истории движений;
- экспорт CSV.

В следующей версии можно добавить:

- webhook;
- периодический обмен;
- импорт справочника товаров;
- выгрузку движений.

### 8. Что делать при потере питания?

Так как замки должны быть fail-secure, без питания они остаются закрытыми.

Но если питание пропало во время открытой сессии:

- после запуска backend увидит активную сессию;
- нужно показать блокирующий экран;
- администратор должен разобраться и завершить операцию.

### 9. Нужен ли механический аварийный доступ?

Для реального шкафа обычно да.

Но аварийное физическое открытие должно сопровождаться ручной инвентаризацией, иначе учет может разъехаться.

## Решения, которые лучше принять до начала кода

1. PostgreSQL или SQLite для первого запуска MVP.
2. Integer ID или UUID.
3. Конкретный тип релейного модуля для MVP.
4. Формат RFID UID после считывателя.
5. Нужна ли история пользователю с ролью `user`.
6. Нужен ли импорт товаров из CSV в MVP.
7. Кто имеет право аварийно завершать сессии.
8. Какой формат экспорта нужен первым: CSV или XLSX.
