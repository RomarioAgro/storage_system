# 11. Разделение работ между агентами или исполнителями

## Зачем делить

Проект удобно разделить на независимые зоны, чтобы несколько исполнителей могли работать параллельно.

Главное: сначала согласовать контракты между зонами:

- модели БД;
- enum-статусы;
- API;
- интерфейс `LockController`;
- правила сессий.

## Агент 1. Архитектор / Tech Lead

### Задачи

- Утвердить структуру проекта.
- Утвердить модели БД.
- Утвердить enum-статусы.
- Утвердить API-контракты.
- Следить за главным правилом: одна активная сессия.
- Ревьюить изменения, которые затрагивают операции и остатки.

### Результаты

- финальная архитектурная схема;
- согласованные интерфейсы;
- список технических решений;
- правила code review.

### Важные файлы

- `00_project_overview.md`;
- `04_database_spec.md`;
- `05_backend_api_spec.md`;
- `10_development_backlog.md`.

## Агент 2. Database / Models

### Задачи

- Реализовать SQLAlchemy-модели.
- Реализовать Alembic-миграции.
- Добавить ограничения и индексы.
- Добавить seed-данные.
- Проверить partial unique index для активной сессии.

### Результаты

- модели БД;
- миграции;
- seed;
- тест создания БД с нуля;
- документация по запуску миграций.

### Критичные требования

- `UNIQUE(cell_id, product_id)`.
- Partial unique index `UNIQUE(cell_id) WHERE quantity > 0`.
- `quantity >= 0`.
- `UNIQUE(rfid_uid)`.
- Partial unique index `only_one_active_cell_session`.

## Агент 3. Backend Core

### Задачи

- Реализовать сервисы:
  - `AuthService`;
  - `PermissionService`;
  - `ProductService`;
  - `CellService`;
  - `StockService`;
  - `AccessLogService`.
- Реализовать API для auth/products/cells.
- Написать unit-тесты.

### Результаты

- работающая авторизация по RFID;
- поиск товаров;
- остатки;
- содержимое ячейки;
- технический журнал.

## Агент 4. Sessions and Operations

### Задачи

- Реализовать `SessionService`.
- Реализовать `OperationService`.
- Реализовать сценарии:
  - `fill`;
  - `take`;
  - `open_only`;
  - `inventory`.
- Реализовать переходы статусов.
- Реализовать защиту от второй активной сессии.
- Написать тесты конкурентных запросов.

### Результаты

- операции меняют остатки только после подтверждения;
- отмена не меняет остатки;
- активная сессия блокирует новые открытия;
- перезапуск сохраняет активную сессию.

### Главная зона риска

Именно здесь чаще всего рождаются учетные призраки: ячейка открылась, товар забрали, но учет не изменился или изменился дважды. Нужны строгие транзакции и тесты.

## Агент 5. Hardware Layer

### Задачи

- Реализовать интерфейс `LockController`.
- Реализовать `MockLockController`.
- Подготовить `UsbRelayController`.
- Подготовить `ModbusRelayController`.
- Описать конфигурацию оборудования.
- Сделать hardware smoke-test.

### Результаты

- backend может работать без железа;
- при наличии железа открывается нужный канал;
- ошибка реле корректно возвращается в backend;
- есть инструкция по настройке.

### Контракт

```python
class LockController:
    def open_cell(
        self,
        controller_address: int,
        relay_channel: int,
        pulse_seconds: float = 1.0,
    ) -> None:
        ...
```

## Рекомендуемый порядок параллельной работы

### Шаг 1. Согласование контрактов

Участвуют:

- архитектор;
- database;
- backend;
- operations;
- hardware;
- UI.

Результат:

- зафиксированы модели;
- зафиксированы API;
- зафиксирован `LockController`;
- зафиксированы статусы.

### Шаг 2. Параллельная разработка

Можно параллельно:

- database делает модели и миграции;
- hardware делает mock и интерфейс;
- backend core делает auth/products/cells;
- UI делает макеты экранов на моковых данных;
- QA пишет тест-кейсы.

### Шаг 3. Интеграция операций

После готовности БД и hardware mock:

- operations реализует fill/take/open_only;
- UI подключается к реальным endpoint;
- QA гоняет основные сценарии.

### Шаг 4. Админка и приемка

- admin panel закрывает управление;
- QA проверяет MVP;
- hardware подключает реальные реле.

## Правила для всех исполнителей

1. Не менять остатки при открытии ячейки.
2. Не открывать ячейку до проверки прав.
3. Не открывать вторую ячейку при активной сессии.
4. Не удалять активную сессию автоматически после перезапуска.
5. Любую ошибку оборудования писать в журнал.
6. Все изменения остатков писать в `stock_movements`.
7. Все важные технические события писать в `access_events`.
8. Не зашивать конкретную плату реле в бизнес-логику.
9. После каждой итерации обновлять соответствующее ТЗ в `spec/`.
10. После каждой итерации создавать локальный HTML-отчет в `reports/` по шаблону `iteration_NNN_short_description.html`; отчеты не коммитить и не пушить.
