# 02. Роли и права доступа

## Роли

В MVP нужны четыре роли:

- `admin`;
- `manager`;
- `user`;
- `service`.

## Общие правила

- Любое действие начинается после RFID-авторизации.
- Неактивный пользователь не получает доступ.
- Неизвестный RFID не получает доступ.
- Все отказанные попытки пишутся в `access_events`.
- Роль проверяется до создания сессии открытия ячейки.
- Если операция запрещена, ячейка не открывается.

## Роль `admin`

Может всё:

- управлять пользователями;
- управлять ролями;
- привязывать RFID;
- блокировать пользователей;
- управлять товарами;
- управлять ячейками;
- управлять остатками;
- проводить пополнение;
- проводить выдачу;
- проводить инвентаризацию;
- открывать ячейки без изменения остатка;
- смотреть историю;
- смотреть журнал доступа;
- управлять оборудованием;
- аварийно завершать активные сессии;
- экспортировать данные.

## Роль `manager`

Может:

- искать товары;
- смотреть остатки;
- смотреть историю;
- создавать товары;
- редактировать товары;
- класть товары;
- забирать товары;
- проводить инвентаризацию;
- смотреть содержимое ячеек.

Не может:

- управлять пользователями;
- менять оборудование;
- аварийно завершать чужие сессии без отдельного разрешения;
- менять роли.

## Роль `user`

Может:

- искать товары;
- смотреть остатки;
- класть товары;
- забирать товары;
- смотреть содержимое ячейки, если это разрешено политикой MVP.

Не может:

- проводить инвентаризацию;
- создавать и редактировать товары;
- управлять пользователями;
- управлять ячейками;
- смотреть технические журналы;
- аварийно завершать сессии.

## Роль `service`

Может:

- открывать ячейки для обслуживания;
- смотреть технические события;
- проверять оборудование.

Не может:

- менять остатки без отдельного разрешения;
- проводить выдачу;
- проводить пополнение;
- редактировать товары.

## Матрица прав MVP

| Действие | admin | manager | user | service |
|---|---:|---:|---:|---:|
| RFID-вход | да | да | да | да |
| Поиск товара | да | да | да | нет |
| Просмотр остатка | да | да | да | нет |
| Просмотр истории товара | да | да | нет/опц. | нет |
| Создать товар | да | да | нет | нет |
| Редактировать товар | да | да | нет | нет |
| Пополнить товар | да | да | да | нет |
| Забрать товар | да | да | да | нет |
| Инвентаризация | да | да | нет | нет |
| Открыть ячейку без изменения остатка | да | опц. | нет | да |
| Управление пользователями | да | нет | нет | нет |
| Управление ячейками | да | нет | нет | нет |
| Управление оборудованием | да | нет | нет | опц. |

| Аварийно завершить сессию | да | опц. | нет | нет |

## Проверка прав в backend

Права должны проверяться в сервисном слое, а не только в UI.

Минимальная схема:

```python
def check_permission(user: User, permission: str) -> None:
    if not user.is_active:
        raise AccessDenied("User is inactive")
    if permission not in user.role.permissions:
        raise AccessDenied("Permission denied")
```

UI может скрывать недоступные кнопки, но backend обязан повторно проверять права.
