# AGENTS.md

## Роль проекта

Этот репозиторий содержит MVP локальной RFID-системы хранения с электронными замками ячеек.

Для больших задач Codex должен работать как главный оркестратор:

- использовать субагентов для read-only анализа перед написанием кода;
- объединять отчеты субагентов в единый план реализации;
- внедрять изменения небольшими последовательными пакетами;
- использовать только одного implementation worker для изменений кода за раз;
- не допускать, чтобы несколько агентов одновременно редактировали одни и те же файлы.

Последовательную реализацию предпочитать для файлов, связанных с:

- моделями;
- миграциями;
- сессиями;
- операциями;
- логикой остатков;
- правами доступа;
- управлением аппаратной частью.

## Критический инвариант

В один момент времени может быть открыта или активна только одна ячейка.

Этот инвариант должен быть защищен на уровне:

- ограничений базы данных;
- сервисной логики;
- поведения API;
- границ транзакций;
- тестов.

Активные статусы `cell_sessions`:

- `created`
- `opening`
- `opened`
- `waiting_close`
- `close_confirmed`

В PostgreSQL инвариант должен быть защищен partial unique index:

```sql
CREATE UNIQUE INDEX only_one_active_cell_session
ON cell_sessions ((true))
WHERE status IN (
    'created',
    'opening',
    'opened',
    'waiting_close',
    'close_confirmed'
);
```

Для SQLite в режиме разработки или тестов инвариант должен быть защищен на уровне сервисов и покрыт тестами.

## Правила учета остатков

Никогда не изменять остатки в момент старта операции.

Остатки можно изменять только после выполнения двух условий:

1. пользователь подтвердил, что ячейка закрыта;
2. пользователь подтвердил операцию.

Отмена операции не должна изменять остатки.

Операции `open_only` не должны изменять остатки.

## Правила аппаратного слоя

Бизнес-логика никогда не должна напрямую управлять релейным оборудованием.

Все операции открытия замков должны проходить через абстракцию `LockController`.

Обязательные реализации:

- `MockLockController` для разработки и тестов;
- `UsbRelayController` только как заглушка;
- `ModbusRelayController` только как заглушка.

Не реализовывать реальные аппаратные протоколы в MVP.

## Правила frontend

Использовать простой терминальный web UI:

- Jinja2;
- HTMX или обычный HTML/JS.

Не использовать React, Vue, Angular или другой тяжелый frontend-фреймворк для MVP.

UI должен показывать блокирующий экран активной сессии, если другая операция с ячейкой не завершена.

## Правило local-first

MVP должен работать локально, без интернета и облачных сервисов.

PostgreSQL использовать для production-like запуска.

SQLite использовать только для локальной разработки или тестов, если проект уже это поддерживает.

## Отчетность

После крупных задач реализации Codex должен сообщать:

- какие субагенты использовались;
- что нашел каждый субагент;
- какой план реализации был выбран;
- какие файлы были изменены;
- какие проверки были запущены;
- какие риски или ограничения остались.

После каждой итерации изменений нужно создавать локальный HTML-отчет в папке `reports/`.
Имя файла должно следовать существующему шаблону `iteration_NNN_short_description.html`,
где `NNN` — следующий номер итерации. Отчеты из `reports/` не добавлять в git и не пушить.
Все выполненные доработки дополнительно описывать в соответствующем ТЗ в папке `spec/`.

 ## Инструменты анализа проекта

  Перед анализом архитектуры, ревью, поиском переусложнений, планированием крупных изменений и перед изменением кода
  Codex должен сначала использовать локальные инструменты индекса:

  1. `ontoindex` — для обзора архитектуры, связей, рисков, impact/diff/pre-commit анализа.
  2. `continuum` — для поиска символов, вызовов, структуры файлов, локального call graph и проектных guideline/
  scratchpad.

  Минимальный порядок:
  - сначала проверить состояние индекса/проекта через `ontoindex`;
  - затем искать код через `continuum` или `ontoindex`, а не только через `rg`;
  - `rg` использовать как fallback или для точного текстового поиска;
  - в итоговом ответе кратко указать, какие инструменты использовались.

  Исключения:
  - простые вопросы без анализа кода;
  - команды вроде `date`, `pytest`, `git status`;
  - если инструмент недоступен или возвращает нерелевантные данные, явно сказать об этом и перейти к обычному поиску.
